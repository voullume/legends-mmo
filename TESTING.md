# Testing Legends MMO

`./play.sh` is the launcher. It assumes Godot at `~/.local/bin/godot`; override with
`GODOT=/path/to/godot ./play.sh …`.

## 1. Quickest — single player (no server, no network)
```
./play.sh            # or: open project.godot in Godot and press F5
```
Log in, pick a class + name (first time), and you're in a local practice world as your
character. Good for trying movement, abilities, and the camera.

Demo account that already has a character:
**`legends_smoke1@testmail.dev` / `Testpass1234!`** — or click **Sign Up** (signups log you
straight in, no email confirmation).

## 2. Two players on one machine
```
./play.sh zone       # starts a headless zone server + opens two player windows
```
Log into **a different account in each window** (sign up a fresh one in the second). You'll see
both characters in the same world. Each account has exactly one character (one class).

To do it by hand instead:
```
godot --headless --path . -- --server        # terminal 1: the zone (no window — that's normal)
godot --path . -- --online                    # terminal 2: player 1 (connects to 127.0.0.1)
godot --path . -- --online                    # terminal 3: player 2
```

## 3. Another person / another machine (LAN)
On the **host** machine:
```
godot --headless --path . -- --server         # find the host's LAN IP, e.g. 192.168.1.50
```
Open **UDP port 7777** in the host's firewall. Everyone else (on the same network) runs:
```
godot --path . -- --online 192.168.1.50 --insecure
```
Each player signs up their own account in their client.

> `--insecure` is required because plaintext ENet to a non-loopback host sends your login token
> unencrypted — the client refuses unless you explicitly opt in (development/LAN only). Loopback
> (`127.0.0.1`) needs no flag.

## 4. A remote user over the internet
There is **no matchmaking/relay** — clients connect straight to the host over ENet/UDP. Two options:

- **VPN (simplest):** put both machines on a mesh VPN like [Tailscale](https://tailscale.com) or
  ZeroTier, then `--online <host-tailscale-ip>`. The VPN encrypts everything; no `--dtls` needed.
- **Public host + DTLS:** if you expose a port to the internet, **encrypt the transport** by
  passing `--dtls` on the server **and** every client. Clients now **verify** the server against a
  pinned certificate (`client/zone_cert.pem`, generated by `deploy/gen_zone_cert.sh` with
  `CN=legends-zone`). For an ad-hoc dev host with no pinned cert, the client must opt in explicitly:
  ```
  # host (forward UDP 7777 to this machine, or run on a cloud VM):
  godot --headless --path . -- --server --dtls          # dev: self-signed; prod: operator cert required
  # remote player, verified (the repo carries the host's public cert as client/zone_cert.pem):
  godot --path . -- --online <public-ip> --dtls
  # remote player, ad-hoc dev host with no pinned cert (encrypts but does NOT verify — dev only):
  godot --path . -- --online <public-ip> --dtls --insecure-dtls
  ```

> ⚠️ **Security:** with the pinned certificate, `--dtls` encrypts **and** verifies the server
> identity (MITM protection). `--insecure-dtls` (source-only) skips verification and prints a loud
> warning. The short-lived access token crosses the wire; the refresh token never leaves the client.
> Production containers (`LEGENDS_ENV=production`) refuse plaintext and refuse to start without a
> persistent operator certificate — see `docs/stabilization.md`.

## 5. Hosting the server (Docker / cloud)
A `Dockerfile` builds a self-contained headless server (downloads Godot, imports assets, runs
`--server --dtls`). The image is the **production profile**: it refuses to start without a valid
`SUPABASE_SERVICE_KEY` **and** a persistent DTLS certificate (exit 1 — fail closed, see
`docs/stabilization.md` §3). `deploy/setup.sh` provisions everything; by hand:
```
docker build -t legends-zone .
deploy/gen_zone_cert.sh /opt/legends-certs      # once per host; commit zone.crt as client/zone_cert.pem
docker run -e SUPABASE_SERVICE_KEY=<service_role> \
  -v /opt/legends-certs:/certs:ro \
  -e LEGENDS_DTLS_CERT=/certs/zone.crt -e LEGENDS_DTLS_KEY=/certs/zone.key \
  -p 7777:7777/udp legends-zone
# throwaway DEV container (self-signed cert; a missing service key only warns):
docker run -e LEGENDS_ENV=development -e SUPABASE_SERVICE_KEY=<key> -p 7777:7777/udp legends-zone
```
**`SUPABASE_SERVICE_KEY`** (Supabase → Settings → API → `service_role`) is required for loot and
equipment to persist: the server is the only writer of the `inventory` table — clients are denied
direct writes, so items can't be forged. On Fly:
`fly secrets set SUPABASE_SERVICE_KEY=<key> LEGENDS_DTLS_CERT_PEM="$(cat zone.crt)" LEGENDS_DTLS_KEY_PEM="$(cat zone.key)"`.
Locally: put the key in a gitignored `.env` (see `.env.example`) — `play.sh` loads it.
Deploy that image anywhere that runs containers with a **UDP** port:
- **A VPS** (Hetzner / DigitalOcean / Vultr — pick **x86_64**, 1 vCPU is enough) — simplest and most
  reliable. One script does the whole box: see **`deploy/README.md`** (`deploy/setup.sh` installs
  Docker, builds, opens the firewall, and runs the container with auto-restart + DTLS).
- **Fly.io** — a starting `fly.toml` is included (`fly apps create … && fly ips allocate-v4 && fly
  deploy`). UDP on Fly needs a **dedicated IPv4** and the `fly-global-services` bind (the toml sets
  `BIND` for that). If routing misbehaves, fall back to the VPS path.
- **Scale-up:** the same image runs on a game-server orchestrator (Hathora, Edgegap, or Agones/K8s).
  Run several zone instances and put a small lobby/gateway in front — the engine, netcode, and
  Supabase persistence don't change.

Common flags: `--port <n>` (bind/connect port), `--dtls` (encrypt), `--bind <ip>` (server bind
address, for hosts that need one), `--online <ip>` (client target).

## Stabilization test suite (offline — no server, no network, no live Supabase)
Headless invariant tests for the online server's security/authority/economy behavior. They boot the
REAL `server/Server.gd` against a deterministic in-memory Supabase fake (`tools/stab/fake_supa.gd`,
with failure injection) and a recording Net fake — nothing touches the live project. Exit non-zero
on any failure (CI-gradeable):
```
godot --headless --path . --script res://tools/stab_auth.gd         # auth, sessions, disconnect cleanup
godot --headless --path . --script res://tools/stab_authority.gd    # movement/ability/ownership/admin/map-restore authority
godot --headless --path . --script res://tools/stab_economy.gd      # legacy economy paths: dupe-safety, refunds, races
godot --headless --path . --script res://tools/stab_econ_atomic.gd  # atomic DB economy: op-ledger idempotency, award flush
godot --headless --path . --script res://tools/stab_sessions.gd     # single-active-session-per-character policy
godot --headless --path . --script res://tools/stab_protocol.gd     # protocol-version handshake
godot --headless --path . --script res://tools/stab_trust.gd        # DTLS/plaintext trust policy (prod vs dev)
```
See `docs/stabilization.md` for what each suite pins down and the remaining known risks.

## In-world controls (zone)
`WASD` move · `1`–`5` abilities · `LMB` basic · `RMB`-drag camera · wheel zoom ·
`Enter` chat · `I` inventory (click items to equip/unequip).

## What works right now (all 5 phases)
Accounts + one locked class per character · a shared persistent zone where players coexist with
interest-managed snapshots · active mobs with aggro/leash on a level/tier gradient · kill → XP →
level-up (+HP) · loot drops that persist · equip gear to boost your stats · zone chat ·
server-authoritative position/XP/loot/equipment persistence to Supabase.

## Notes & known limits (prototype)
- One character per account (class is permanent).
- Inventory is **server-authoritative**: only the zone server writes it (service_role via
  `SUPABASE_SERVICE_KEY`) — clients can't forge items. Set that env var or loot/equip won't persist.
- No chat rate abuse (1.4 msg/s/player) and equip is rate-limited + serialized.
- `--autowalk` is a debug flag (a bot that fights, chats, and equips) used by the test scripts.
